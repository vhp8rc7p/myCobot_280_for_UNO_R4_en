# 6.1.4 Transponder mode

Transponder mode turns the UNO R4 into a transparent bridge between the PC and
the arm, so `pymycobot` on the host drives the arm directly. It is the
equivalent of the `Uart` mode in the M5 RoboFlow firmware.

```
PC (python)  <--USB CDC-->  [Serial] UNO R4 [Serial1]  <--D0/D1-->  myCobot 280
```

The R4 forwards most bytes verbatim in both directions, and answers a small set
of commands itself — the ones addressed to the *controller board* rather than
to the arm's Atom.

## Two options

### Option A — prebuilt project (recommended)

[**MyCobot280_R4_Transponder**](https://github.com/vhp8rc7p/MyCobot280_R4_Transponder)
bundles the handful of library files it needs, already configured for the R4.
No library install, no `ParameterList.h` edit, nothing to remember. Open the
`.ino`, select **Arduino UNO R4 WiFi**, upload.

It also adds scrolling text on the [LED matrix](10.5-led_matrix.md).

### Option B — the official example

`examples/MyCobot280/MyCobot280_Arduino/Mkr/Transponder/Transponder.ino` from
the `MyCobotBasic` library, after configuring `ParameterList.h` and applying
the one-line `data` → `rx_byte` rename. Both steps are in
[6.1.2 Simple Use](10.2-arduino_use.md).

## Commands answered locally

Some commands address the controller board, not the arm. The Atom will never
reply to them, so the transponder must:

| Code | Command | Behaviour |
|---|---|---|
| `0xc1` | `GET_BASIC_VERSION` | returns `SYSTEM_VERSION` |
| `0xc2` | `SET_COMMUNICATE_MODE` | toggles transparent pass-through |
| `0xc3` | `GET_COMMUNICATE_MODE` | returns the current mode |
| `0xa0` | `SET_BASIC_OUT` | `digitalWrite` on an R4 pin |
| `0xa1` | `GET_BASIC_IN` | `digitalRead` on an R4 pin |

Everything else is forwarded to the arm unchanged.

The official `Mkr/Transponder.ino` implements only `0xa0` and `0xa1`. The
prebuilt project adds `0xc1`/`0xc2`/`0xc3`, matching the M5 firmware more
closely — so `get_basic_version()` works rather than timing out.

### Frame format

```
FE FE <len> <cmd> [payload...] FA
```

`len` counts everything after itself, including the `FA` terminator, so the
total frame is `3 + len` bytes.

```
fe fe 02 c1 fa           GET_BASIC_VERSION  (len=2: c1, fa)
fe fe 03 c1 18 fa        reply              (len=3: c1, 0x18, fa)
```

## Verifying without the arm

`GET_BASIC_VERSION` is answered by the R4 itself, so it tests the board and USB
link in isolation — **no arm, no arm power required**:

```
send: fe fe 02 c1 fa
recv: fe fe 03 c1 18 fa
```

`0x18` = 24 = `SYSTEM_VERSION` for a myCobot 280, reported by `pymycobot` as
`2.4`. If you see `0x0d` (13) instead, the sketch was built against
`MyPalletizerBasic.h` rather than `MyCobotBasic.h`.

If this works but `get_angles()` still returns `-1`, the fault is between the
R4 and the arm — see
[5.3 Hardware Interface](../../5.BasicFunction/5.3-HardwareInterface/RoboticArmElectricalInterface.md).

## Using it

```python
import time
from pymycobot import MyCobot280

mc = MyCobot280("COM13", 115200)
time.sleep(2.5)                      # the R4 resets when the port opens

print(mc.get_angles())
mc.send_angles([0, 0, 0, 0, 0, 0], 20)
```

See [6.2 Python](../python/README.md) for the full host-side guide.

## A note on blocking

A transponder must never block. Anything that stalls `loop()` — a long
`delay()`, a blocking animation, a synchronous network call — stops the serial
pump and drops arm traffic.

This matters concretely for the LED matrix: the obvious API,
`matrix.endText(SCROLL_LEFT)`, blocks for the entire scroll. See
[6.1.5 LED matrix](10.5-led_matrix.md) for the non-blocking approach.

Measured through the prebuilt transponder with the matrix animating,
40 consecutive `get_angles()` calls:

| | |
|---|---|
| malformed replies | 0 / 40 |
| median latency | 17.8 ms |
| max latency | 57.9 ms |
